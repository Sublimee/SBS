# Пример 2

```java
private static List<DocumentDto> buildDocuments(
        Page<DocumentEntity> documentEntityPage,
        Map<UUID, List<PaymentHistoryEntity>> paymentHistoryByIdMap,
        boolean useV2
) {

    return documentEntityPage.stream()
            .map(
                    document -> {
                        var paymentHistoryList = paymentHistoryByIdMap.getOrDefault(document.getId(), emptyList());
                        return useV2 ? buildDocumentDtoV2(document, paymentHistoryList)
                            : buildDocumentDto(document, paymentHistoryList);
                    }
            )
            .toList();
}
```

Сам метод и общая часть достаточно короткие, чтобы использовать сигнатуру с useV2 всего в двух местах в коде.

# Вывод

В первом примере затронут случай, когда создаётся второй эндпоинт с новым контрактом относительно существующего. На моей практике встречались оба сценария:

1) поддержка двух независимых реализаций. Рассчитываем, что одну из реализаций уберем из кода целиком и не нарушим логику другой реализации вовсе. PR будет преимущественно состоять из удалённых файлов. Однако, если вдруг в переходный период надо поддержать пришедшие правки в обеих реализациях, то можно забыть это сделать во всех местах. Справиться с этим помогают "задублированные" для каждой ветки тесты. Скорее подходит, когда реализации отличаются очень сильно.

2) поддержка одной реализаций с "ветвлениями" (if, динамическая типизация и другое) для каждого случая. Рассчитываем на то, что дублирования кода будет слишком много и часто приходящие правки будет проблематично внедрять. Убирать такую логику сложнее, PR будет состоять преимущественно из изменённых файлов. Проблема в наличии двух сценариев опять же решается тестами. Скорее подходит, когда реализации отличаются мало.

В первом случае недавно столкнулись с тем, что вторая рядом стоящая реализация повторила первую не точь-в-точь. В связи с отсутствием "дублирующих" тестов получили баг на проде.

Выбор между вариантами должен происходить на основании эмпирического опыта при работе с конкретным проектом и заказчиками. У нас были такие переходные периоды длиной в 6+ месяцев. В этом случае расщеплять разные логики, связанные в одну реализацию сложнее по понятным причинам (как минимум выше когнитивная нагрузка на разработчика).

Аналогичные идеи актуальны и для случая, когда идёт миграции подкапотной логики эндпоинта на новую с сохранением контракта (второй пример).
