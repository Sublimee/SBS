Попытался найти примеры не только на уровне NULL в БД, но и в других местах.

# Пример 1

На разных шагах процесса двухфакторной аутентификации использовался один и тот же ответ:

```kotlin
data class TfaStatusResponse(
    val phone: String?,
    val maskedPhone: String?
)
```

Возможны четыре вариации заполнения объекта, но только две из них корректны. В том случае даже не требовался sealed interface, можно было просто разделить класс на два и каждый использовать только в своём сценарии. Видимо, не хватило фантазии, чтобы дать имена двум похожим классам.

# Пример 2

В одном из проектов для того, чтобы поддержать разные "действия", использовали такую схему, которую предоставляет jackson:

```java
@JsonSubTypes({
        @JsonSubTypes.Type(value = RepeatAction.class, name = "REPEAT"),
        @JsonSubTypes.Type(value = BaseAction.class, name = "SPLIT"),
        ...
})
public interface Action {

    String getType();

    String getLabel();

    Icon getIcon();
}
```

В итоге вместо единственного multy responsibility DTO получили ряд классов, экземпляры которых заполняются однозначно (все поля non nullable).

# Пример 3

Банальный пример. Флаг просмотра пользователем информационного окна после регистрации:

```java
@Column(name = "viewed_after_registration_modal")
private Boolean isModalViewed;
```

Здесь зачем-то введено третье состояние в виде null, но судя по коду оно не используется. Тем не менее тип такого поля в БД лучше сократить до BOOLEAN NOT NULL DEFAULT FALSE: по умолчанию проставляем "ещё не просмотрено". А еще лучше использовать дату, тогда NULL всё же будет, но его причина будет однозначно считываться из названия колонки.

# Пример 4

В системе есть сущность «подписант». Подписант может загружать документ и удалять его. Сейчас нельзя различить состояния документа "не предоставлен" и "удалён". Если внести статус, то мы сможем различать состояния:

```sql
file_charter        VARCHAR(...)
file_charter_state  SMALLINT NOT NULL

-- 0 = не предоставлен
-- 1 = предоставлен
-- 2 = удалён
```

Если же нужна историчность удалений и загрузок, то нужно хранить такую последовательность событий в отдельной таблице.

# Пример 5

В проекте хранятся настройки офферов, включая адреса офлайн-магазинов, где можно воспользоваться предложением. Отсутствие адресов сейчас можно трактовать по-разному: пользователь ещё не предоставил их, либо они не применимы, так как магазин работает исключительно онлайн.

Причину отсутствия стоит хранить явно:

```sql
offline_addresses_state SMALLINT NOT NULL

-- 0 = адреса не предоставлены
-- 1 = нет офлайн точек 
```

# Вывод

Проблема null -- это проблема сделать невозможным появления в системе некорректного состояния. Это значение/состояние/опция, которое встроено обычно по умолчанию. Но оно нам зачастую не нужно, отсюда возникает конфликт, который требуется решать.

Один из вариантов, если это возможно, использовать non-nullable типы. Тогда состояние `null` просто невозможно (примеры 1 и 2). Проблема решена.

Если мы говорим про SQL, то у нас есть возможность задавать через DDL non-nullable типы (пример 3). Если же null -- одно из валидных значений, то, как в примерах 4 и 5, мы должны однозначно его интерпретировать. Для поддержания консистентности данных (поле заполнено как `null`, но числовое обозначение указывает на тип, отличный от `null`) требуется вводить ограничения на уровне таблицы (DDL), чтобы не было возможности неправильно заполнить колонки. Это вносит частично логику в БД, что может быть проблемой, так как требуется её синхронизация на уровне кодовой базы сервиса, который взаимодействует с этой таблицей. 

Возникает вопрос: а нужно ли всегда обогащать каждое такое nullable поле дополнительной информацией о статусе? В примере 3 кажется, что это избыточно. В примерах 4 и 5, если мы возвращаемся к мысли, что мы не хотим сами у себя воровать семантику, то это отличная идея.

Почему, если речь зашла о семантике, тогда каждое изменение строки в БД не сопровождать событием аудита, которое зафиксирует переход между состояниями? Иногда это обязательное требование для каких-то важных сущностей или когда мы хотим поддержать какой-то значимый, важный процесс. Но это всё же некоторая дополнительная информация, которая может никогда не понадобиться. Здесь надо соблюдать баланс и думать в рамках своей предметной области и, в идеале, понимать вектор развития продукта. Конечно, чем больше опыта при развитии аналогичных фич, тем больше таких подводных камней можно избежать, сохранив какую-то дополнительную семантику. 

В примерах 4 и 5 мы все же хотим добиться однозначности интерпретации уже хранимых данных, чтобы избежать ошибок этой самой интерпретации.
